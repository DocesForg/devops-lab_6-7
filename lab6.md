# Отчёт по лабораторной работе №6
## Основы микросервисной архитектуры

**Вариант:** 6 — сервис «Сотрудники».  
**Цель:** реализовать микросервис с операциями создания сотрудника, получения по идентификатору и изменения должности, разделить бизнес-логику и транспорт и предоставить HTTP- и gRPC-интерфейсы.

## 1. Постановка задачи

Реализуется сущность `Employee` со следующими полями:

| Поле | Тип | Назначение |
|---|---|---|
| `ID` | string | уникальный идентификатор |
| `FullName` | string | ФИО сотрудника |
| `Position` | string | должность |
| `Salary` | float64 | заработная плата |
| `HiredOn` | int64 | дата найма в формате Unix timestamp |

Операции сервиса:

- `Create(ctx, employee) (string, error)` — создать сотрудника и вернуть ID;
- `GetByID(ctx, id) (Employee, error)` — получить сотрудника;
- `ChangePosition(ctx, id, position) error` — изменить должность.

## 2. Архитектура

- **Модель и репозиторий — `employee.go`.** `Employee` описывает предметную сущность. `EmployeeRepository` скрывает способ хранения, а `MemoryRepository` реализует потокобезопасное хранение в map.
- **Бизнес-слой — `service.go`.** Интерфейс `EmployeeService` задаёт операции и используется обоими транспортами.
- **Go kit endpoints и gRPC-адаптер — `grpc.go`.** Каждый endpoint вызывает бизнес-сервис через интерфейс. Go kit `transport/grpc` выполняет декодирование запроса, вызов endpoint и кодирование ответа. gRPC сервер слушает порт `9090`.
- **HTTP-адаптер — `http.go`.** Обрабатывает JSON и возвращает соответствующие HTTP-статусы. HTTP сервер слушает порт `8080`.
- **Контракт — `employee.proto`.** Описывает сервис `employee.v1.EmployeeService` и методы `Create`, `GetByID`, `ChangePosition`. Для компактного примера сообщения имеют тип `google.protobuf.Struct`.
- **Точка входа — `main.go`.** Создаёт общий сервис, запускает HTTP и gRPC серверы и выполняет graceful shutdown при SIGINT/SIGTERM.

Слои отделены друг от друга: оба транспорта используют одну бизнес-логику и один репозиторий, поэтому поведение операций не дублируется в транспортных обработчиках.

## 3. HTTP API

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/employees` | создать сотрудника |
| GET | `/employees/{id}` | получить сотрудника |
| PATCH | `/employees/{id}/position` | изменить должность |
| GET | `/healthz` | проверка HTTP-сервера |

Для некорректного JSON и неверных полей возвращается `400 Bad Request`; для отсутствующего сотрудника — `404 Not Found`. Сервер ограничивает размер тела запроса, задаёт ReadHeaderTimeout и логирует обращения.

## 4. gRPC API и Go kit

Адрес по умолчанию — `:9090`. В `grpc.go` определены три Go kit endpoint, функции декодирования protobuf `Struct` в запросы сервиса, кодирование ответов и регистрация методов в gRPC сервере.

Ошибки предметной области преобразуются в gRPC status codes:

- `ErrInvalid` → `InvalidArgument`;
- `ErrNotFound` → `NotFound`;
- непредвиденная ошибка → `Internal`.

Пример создания сотрудника с помощью установленного `grpcurl`:

```bash
grpcurl -plaintext -import-path . -proto employee.proto \
  -d '{"full_name":"Иван Иванов","position":"Инженер","salary":80000}' \
  localhost:9090 employee.v1.EmployeeService/Create
```

Получение и изменение должности:

```bash
grpcurl -plaintext -import-path . -proto employee.proto \
  -d '{"id":"1"}' localhost:9090 employee.v1.EmployeeService/GetByID

grpcurl -plaintext -import-path . -proto employee.proto \
  -d '{"id":"1","position":"Ведущий инженер"}' \
  localhost:9090 employee.v1.EmployeeService/ChangePosition
```

ID `1` приведён как пример для первого сотрудника в новом процессе. В репозитории есть интеграционный тест `grpc_test.go`, который проверяет создание, чтение и изменение должности через gRPC-вызовы.

**Примечание о формате:** транспорт использует стандартное protobuf-сообщение `google.protobuf.Struct`, а не отдельные типизированные сообщения `Employee`. Файл `employee.proto` задаёт контракт, но сгенерированные protobuf-типы не используются. Для учебного примера это позволяет показать полноценный gRPC-вызов и Go kit transport без генерации кода; для промышленного API предпочтительны типизированные protobuf-сообщения.

## 5. Запуск и проверка

```bash
go mod download
go test -race ./...
go vet ./...
go run .
```

HTTP слушает `:8080`, gRPC — `:9090`. Переопределение адресов:

```bash
go run . -http.addr=:8081 -grpc.addr=:9091
```

Docker-образ открывает порты `8080` и `9090`.

## 6. Результат и ограничения

Реализованы бизнес-сервис и in-memory репозиторий, HTTP JSON API, Go kit endpoints, gRPC транспорт на порту `9090`, protobuf-контракт, обработка ошибок и интеграционный gRPC-тест. Оба транспорта используют общий экземпляр бизнес-сервиса.

Данные хранятся в памяти и не переживают перезапуск процесса. Для эксплуатации следует добавить постоянное хранилище, аутентификацию, авторизацию и TLS.
