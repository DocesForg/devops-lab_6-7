# Отчёт по лабораторной работе №6
## Основы микросервисной архитектуры

**Вариант:** 6 — сервис «Сотрудники».  
**Цель:** изучить основы микросервисной архитектуры и реализовать сервис с операциями создания сотрудника, получения по идентификатору и изменения должности.

## 1. Постановка задачи

Реализуется сущность `Employee` со следующими полями:

| Поле | Тип | Назначение |
|---|---|---|
| `ID` | string | уникальный идентификатор |
| `FullName` | string | ФИО сотрудника |
| `Position` | string | должность |
| `Salary` | float64 | заработная плата |
| `HiredOn` | int64 | дата найма в формате Unix timestamp |

Необходимые операции:

- `Create(ctx, employee) (string, error)` — создать сотрудника и вернуть ID;
- `GetByID(ctx, id) (Employee, error)` — получить сотрудника;
- `ChangePosition(ctx, id, position) error` — изменить должность.

## 2. Архитектура

В проекте разделены модель и доступ к данным (`employee.go`), бизнес-операции (`service.go`), HTTP API (`http.go`) и запуск приложения (`main.go`).

- **Модель и репозиторий.** `Employee` описывает предметную сущность. Интерфейс `EmployeeRepository` скрывает способ хранения. `MemoryRepository` реализует хранение в map с синхронизацией через mutex.
- **Сервисный слой.** Интерфейс `EmployeeService` определяет бизнес-операции. Реализация проверяет обязательные поля и передаёт запросы репозиторию.
- **Транспортный слой.** HTTP-обработчики принимают JSON, вызывают сервис и возвращают JSON-ответы с HTTP-статусами.
- **Точка входа.** `main.go` создаёт зависимости, запускает HTTP-сервер, пишет логи и выполняет graceful shutdown при SIGINT/SIGTERM.

Такое разделение позволяет тестировать бизнес-логику отдельно от HTTP и заменить in-memory хранилище другой реализацией без изменения интерфейса сервиса.

## 3. HTTP API

| Метод | Путь | Назначение | Успешный ответ |
|---|---|---|---|
| POST | `/employees` | создать сотрудника | `201 Created`, JSON с `id` |
| GET | `/employees/{id}` | получить сотрудника | `200 OK`, объект Employee |
| PATCH | `/employees/{id}/position` | изменить должность | `200 OK` |
| GET | `/healthz` | проверка работоспособности | `200 OK` |

Для некорректного JSON и неверных полей возвращается `400 Bad Request`; для отсутствующего сотрудника — `404 Not Found`. Сервер ограничивает размер тела запроса, задаёт ReadHeaderTimeout и логирует обращения.

## 4. Запуск и проверка

```bash
go test -race ./...
go vet ./...
go run .
```

Создание сотрудника:

```bash
curl -i -X POST http://localhost:8080/employees \
  -H 'Content-Type: application/json' \
  -d '{"full_name":"Иван Иванов","position":"Инженер","salary":80000}'
```

Из ответа нужно взять `id`, затем выполнить:

```bash
curl http://localhost:8080/employees/1
curl -i -X PATCH http://localhost:8080/employees/1/position \
  -H 'Content-Type: application/json' \
  -d '{"position":"Ведущий инженер"}'
curl http://localhost:8080/healthz
```

ID `1` приведён как пример для первого сотрудника в новом процессе. Тесты в `employee_test.go` проверяют жизненный цикл сотрудника, ошибку при обращении к несуществующему ID, а также HTTP-сценарий создания и получения.

## 5. Результат и ограничения

Подготовлен Go-сервис с HTTP JSON API, интерфейсами сервиса и репозитория, in-memory хранилищем, обработкой ошибок, логированием и тестами. Данные сохраняются между запросами в рамках одного запуска, но не переживают перезапуск процесса.

**Ограничение относительно методических указаний:** в текущей версии не подключены библиотеки Go kit и не реализован второй gRPC-транспорт на порту 9090; реализован HTTP-транспорт на порту 8080. Для полного соответствия третьему заданию лабораторной требуется добавить `.proto`, сгенерированный код и gRPC-адаптеры. Это ограничение отмечено явно, чтобы отчёт не утверждал о непроверенной функциональности.
