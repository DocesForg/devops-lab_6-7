# Отчёт по лабораторной работе № 7
## Настройка CI/CD и автоматизированных проверок безопасности

**Вариант:** 6 — проверки безопасности Go-приложения.

## 1. Цель работы

Изучить принципы непрерывной интеграции и доставки (CI/CD), настроить GitHub Actions для автоматической сборки и тестирования Go-приложения, подключить статический анализ и проверку зависимостей на известные уязвимости, а также автоматизировать сборку контейнерного образа Docker.

## 2. Задание

Для микросервиса сотрудников из лабораторной работы № 6 требуется настроить автоматизированные workflow, которые запускаются при изменении кода. Проверки должны включать сборку, тестирование, анализ кода, поиск уязвимостей и создание Docker-образа. Публикация образа должна использовать секреты GitHub Actions, а не хранить учётные данные в репозитории.

## 3. Организация CI/CD

В репозитории используются два workflow:

1. `.github/workflows/ci.yml` — сборка, тестирование, статические проверки и анализ безопасности.
2. `.github/workflows/docker.yml` — сборка Docker-образа и публикация в Docker Hub при наличии необходимых секретов.

Workflow CI запускается при push и pull request в ветку `main`, а также вручную. Docker workflow собирает образ при предусмотренных событиях, но не публикует его из pull request.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* каталог `.github/workflows` в репозитории, где видны файлы `ci.yml` и `docker.yml`.

## 4. Настройка непрерывной интеграции

Workflow CI выполняет следующие действия:

1. Получает исходный код репозитория.
2. Устанавливает Go.
3. Загружает зависимости и проверяет состояние модулей.
4. Собирает приложение командой `go build -v ./...`.
5. Запускает тесты с детектором гонок и формированием профиля покрытия: `go test -v -race -coverprofile=coverage.out ./...`.
6. Выполняет статический анализ командой `go vet ./...`.
7. Запускает `govulncheck` для поиска применимых известных уязвимостей.
8. Запускает `gosec` для поиска распространённых небезопасных конструкций в исходном коде.
9. Загружает профиль покрытия как артефакт workflow.

В конфигурации используется матрица версий Go: заданная версия и актуальная стабильная версия. Инструменты security-анализа запускаются в задании стабильной версии, чтобы избежать повторной установки. Для workflow применяется минимальное разрешение `contents: read`, если более широкие права не требуются конкретному шагу.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* файл `.github/workflows/ci.yml` в GitHub или IDE — чтобы были видны события запуска и основные шаги сборки, тестирования и анализа.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* вкладку **Actions** с завершённым запуском CI workflow и зелёным статусом успешного выполнения. Если запуск завершился ошибкой, сначала устраните её; не представляйте неуспешный запуск как успешный.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* раскрытые шаги успешного CI-запуска, где видны результаты сборки, тестов, `go vet`, `govulncheck` и `gosec`.

## 5. Используемые проверки безопасности

| Инструмент | Назначение | Команда |
|---|---|---|
| `go vet` | обнаружение подозрительных конструкций и вероятных ошибок | `go vet ./...` |
| `govulncheck` | проверка применимых опубликованных уязвимостей Go и зависимостей | `govulncheck ./...` |
| `gosec` | поиск распространённых небезопасных паттернов в исходном коде | `gosec -exclude-generated ./...` |

Эти инструменты решают разные задачи и дополняют друг друга. Успешное прохождение проверок не означает абсолютного отсутствия уязвимостей: результаты анализа необходимо оценивать с учётом контекста приложения и актуальности базы уязвимостей.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* логи завершённых шагов `govulncheck` и `gosec` в GitHub Actions. На снимке должны быть видны названия шагов и итоговый статус.

## 6. Сборка Docker-образа

В репозитории используется многоэтапный Dockerfile:

- на этапе сборки применяется образ Go для компиляции приложения;
- в финальный образ копируются исполняемый файл и необходимые сертификаты;
- приложение запускается от непривилегированного пользователя;
- используются порты **8080** для HTTP и **9090** для gRPC.

Такой подход позволяет не включать компилятор и исходный код в финальный контейнер, уменьшая его размер и количество лишних компонентов.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* содержимое `Dockerfile`, где видны этап сборки, финальный образ и команда запуска приложения.

## 7. Публикация образа и секреты

Для публикации в Docker Hub workflow использует два секрета репозитория:

- `DOCKERHUB_USERNAME` — имя пользователя Docker Hub;
- `DOCKERHUB_TOKEN` — Personal Access Token Docker Hub с необходимыми правами на публикацию.

Секреты настраиваются в **Settings → Secrets and variables → Actions**. Их значения нельзя помещать в исходный код, отчёт или скриншоты. В отчёте следует показывать только имена секретов, не их значения.

Образ публикуется под именем `docker.io/docesforg/devops-lab-6-7`. Если секреты отсутствуют или недоступны, workflow должен пропустить вход в Docker Hub и всё равно выполнить сборку образа, сообщив, что публикация не выполнялась. Успешную публикацию следует подтверждать отдельно по результату workflow и наличию образа в Docker Hub.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* страницу **Settings → Secrets and variables → Actions**, где видны только имена `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`. Значения секретов не должны быть раскрыты.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* успешный запуск Docker workflow во вкладке **Actions**, включая итог сборки образа. Если секреты настроены и публикация выполнена, покажите также шаг публикации.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* страницу репозитория Docker Hub с образом `docesforg/devops-lab-6-7` и опубликованным тегом. Этот снимок нужен только в том случае, если образ действительно опубликован.

## 8. Кэширование и артефакты

Для ускорения сборки используется кэширование Go-модулей через `actions/setup-go`. Профиль покрытия тестами `coverage.out` сохраняется как artifact, чтобы его можно было скачать после выполнения workflow и просмотреть локально:

```powershell
go tool cover -html=coverage.out
```

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* раздел **Artifacts** успешного CI-запуска, где отображается артефакт `coverage`. При наличии скачанного профиля можно дополнительно показать HTML-отчёт покрытия.

## 9. Проверка результата

В Windows локальные проверки можно выполнять из **PowerShell** (например, во встроенном терминале VS Code). Команды Go одинаковы для Windows и Linux:

```powershell
go mod download
go test -race -coverprofile=coverage.out ./...
go vet ./...
go build ./...
```

После отправки изменений в GitHub необходимо открыть вкладку **Actions**, дождаться завершения workflow и проверить результаты всех шагов. Наличие файлов YAML в репозитории само по себе не подтверждает успешное выполнение: в отчёт следует вставить снимки реальных запусков. Если запуск завершился неудачно, необходимо указать это и устранить ошибку перед повторной проверкой.

Для дополнительной защиты ветки `main` рекомендуется запретить прямые изменения, потребовать pull request и настроить обязательные проверки после того, как workflow хотя бы один раз успешно выполнится.

**СКРИНШОТ ЗДЕСЬ**

*Что заскринить:* страницу GitHub Actions с итоговым состоянием обоих workflow — CI и Docker — после завершения запусков.

## 10. Результаты работы

Подготовлены workflow GitHub Actions для автоматической проверки Go-микросервиса и сборки контейнера. CI включает сборку, тесты с race detector и покрытием, `go vet`, `govulncheck` и `gosec`. Отдельный workflow отвечает за Docker-сборку и публикацию образа при наличии настроенных секретов.

## 11. Вывод

В результате лабораторной работы изучен и настроен процесс CI/CD для Go-приложения. Автоматизация позволяет выполнять повторяемые проверки при изменениях кода, раньше выявлять ошибки и потенциальные проблемы безопасности, а также стандартизировать сборку Docker-образа. Учётные данные Docker Hub передаются через GitHub Secrets, а успешность проверок и публикации подтверждается фактическими результатами workflow.
