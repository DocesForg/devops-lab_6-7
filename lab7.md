# Отчёт по лабораторной работе №7
## CI/CD для Go-микросервиса на GitHub Actions

**Вариант:** 6 — безопасность.  
**Цель:** автоматизировать сборку и тестирование Go-проекта, а также добавить статические проверки и анализ уязвимостей.

## 1. Реализованные workflow

### 1.1. CI — `.github/workflows/ci.yml`

Workflow запускается при `push` и `pull_request` в ветку `main`, а также вручную через `workflow_dispatch`. Используется матрица Go 1.21 и 1.22; `fail-fast: false` позволяет увидеть результат обеих сборок.

Последовательность шагов:

1. `actions/checkout@v4` — получить исходный код.
2. `actions/setup-go@v5` — установить соответствующую версию Go и настроить кэширование модулей.
3. `go mod download` — загрузить зависимости.
4. `go build -v ./...` — проверить компиляцию.
5. `go test -v -race -coverprofile=coverage.out ./...` — запустить тесты, детектор гонок и сохранить покрытие.
6. `go vet ./...` — выполнить статический анализ средствами Go.
7. `govulncheck ./...` — проверить используемые зависимости и код на известные уязвимости Go.
8. `gosec ./...` — выполнить статический анализ распространённых проблем безопасности.
9. `actions/upload-artifact@v4` — сохранить `coverage.out` как артефакт.

Security-инструменты выполняются в одном из матричных заданий, чтобы не устанавливать их дважды. Workflow использует минимальные права `contents: read`.

### 1.2. Docker — `.github/workflows/docker.yml`

Отдельный workflow запускается при push в `main`, push тегов `v*`, pull request и вручную. Он настраивает Docker Buildx, формирует метаданные и теги образа, затем выполняет multi-stage сборку.

При pull request образ только собирается. Публикация выполняется на push и требует секретов репозитория:

- `DOCKERHUB_USERNAME` — имя пользователя Docker Hub;
- `DOCKERHUB_TOKEN` — токен Docker Hub.

Секреты задаются в **Settings → Secrets and variables → Actions** и не хранятся в исходном коде. В workflow не передаётся пароль в открытом виде.

## 2. Dockerfile

Сборка выполняется в два этапа:

- `golang:1.22-alpine` используется для компиляции приложения;
- в финальный `alpine:3.20` копируется только исполняемый файл и сертификаты.

В финальном образе приложение запускается от непривилегированного пользователя. Порт приложения — 8080. Это уменьшает размер образа и снижает привилегии процесса.

## 3. Проверки безопасности: вариант 6

| Инструмент | Что проверяет | Команда |
|---|---|---|
| `go vet` | подозрительные конструкции и вероятные ошибки в коде | `go vet ./...` |
| `govulncheck` | известные уязвимости Go, применимость кода и зависимостей | `govulncheck ./...` |
| `gosec` | распространённые небезопасные конструкции в исходном коде | `gosec ./...` |

Эти инструменты дополняют друг друга: `go vet` нацелен на корректность кода, `govulncheck` — на опубликованные уязвимости, а `gosec` — на статические security-паттерны. Ни один сканер не гарантирует абсолютную безопасность, поэтому найденные предупреждения необходимо анализировать.

## 4. Кэширование и артефакты

`actions/setup-go@v5` включает кэширование Go-модулей на основании `go.mod`. Это позволяет повторно использовать загруженные зависимости в следующих запусках. Профиль покрытия сохраняется как artifact с именем `coverage` и сроком хранения 14 дней.

После скачивания артефакта покрытие можно просмотреть локально:

```bash
go tool cover -html=coverage.out
```

## 5. Проверка результата

Локальные команды для первичной проверки:

```bash
go test -race -coverprofile=coverage.out ./...
go vet ./...
go build ./...
```

После отправки изменений в GitHub необходимо открыть вкладку **Actions**, дождаться завершения workflow и проверить логи шагов Build, Test, go vet, govulncheck и gosec. Для проверки публикации Docker-образа необходимо настроить оба секрета Docker Hub и проверить наличие тегов в реестре.

**Статус проверки:** файлы workflow и проект добавлены в репозиторий, однако успешный запуск GitHub Actions, фактическая публикация образа и настройка branch protection не заявляются как выполненные: для них требуются реальные запуски workflow, секреты Docker Hub и изменение настроек репозитория.

## 6. Защита ветки

Рекомендуемая настройка GitHub: **Settings → Branches / Rulesets** — запретить прямые изменения в `main`, потребовать pull request и успешные обязательные проверки CI. Конкретные названия required checks нужно выбрать после первого запуска workflow, когда GitHub зарегистрирует job'ы.

## 7. Вывод

Настроен CI-процесс для двух версий Go, автоматическая сборка и тесты с проверкой гонок и покрытием, статический анализ и security-сканирование, а также отдельный Docker workflow с multi-stage сборкой и публикацией при наличии секретов. Это переносит повторяемые проверки в автоматизированный конвейер и помогает обнаруживать ошибки до слияния изменений.
