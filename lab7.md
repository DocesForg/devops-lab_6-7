# Отчёт по лабораторной работе №7
## CI/CD для Go-микросервиса на GitHub Actions

**Вариант:** 6 — безопасность.  
**Цель:** автоматизировать сборку, тестирование, статический анализ, поиск уязвимостей и сборку контейнерного образа.

## 1. Реализованные workflow

### 1.1. CI — `.github/workflows/ci.yml`

Workflow запускается при push и pull request в ветку `main`, а также вручную через `workflow_dispatch`. Используется матрица Go `1.27.1` и `stable`, чтобы проверять код на поддерживаемой версии и на актуальном стабильном выпуске Go. Это также позволяет не запускать анализ стандартной библиотеки на устаревшей версии Go, в которой сканер уже обнаруживает исправленные уязвимости.

Последовательность шагов:

1. `actions/checkout@v4` — получить исходный код.
2. `actions/setup-go@v5` — установить Go и настроить кэш модулей.
3. `go mod download` — загрузить зависимости.
4. `go build -v ./...` — проверить компиляцию.
5. `go test -v -race -coverprofile=coverage.out ./...` — запустить тесты с детектором гонок и сохранить покрытие.
6. `go vet ./...` — выполнить статический анализ средствами Go.
7. `govulncheck ./...` — проверить известные уязвимости в стабильной версии Go.
8. `gosec ./...` — выполнить статический security-анализ.
9. `actions/upload-artifact@v4` — сохранить `coverage.out` как артефакт.

Security-инструменты запускаются только в матричном задании `stable`, чтобы не устанавливать их дважды. Используется минимальное разрешение `contents: read`.

### 1.2. Docker — `.github/workflows/docker.yml`

Workflow запускается при push в `main`, push тегов `v*`, pull request и вручную. Он настраивает Docker Buildx, формирует метаданные и теги образа, затем выполняет multi-stage сборку.

- При pull request образ собирается, но не публикуется.
- При push образ публикуется, если оба секрета Docker Hub доступны в workflow.
- Если один или оба секрета не заданы/недоступны, шаг входа пропускается, образ всё равно собирается, а workflow выводит пояснение вместо ошибки авторизации.

Необходимые repository secrets:

- `DOCKERHUB_USERNAME` — имя пользователя Docker Hub;
- `DOCKERHUB_TOKEN` — Personal Access Token Docker Hub с правом Read & Write.

Секреты настраиваются в **Settings → Secrets and variables → Actions**. Они не должны храниться в исходном коде или выводиться в логи. Имя образа — `docker.io/docesforg/devops-lab-6-7` (нижний регистр).

## 2. Dockerfile

Сборка выполняется в два этапа:

- `golang:1.27-alpine` используется для компиляции приложения;
- в финальный `alpine:3.22` копируется только исполняемый файл и сертификаты.

Приложение запускается от непривилегированного пользователя. Открыты порты `8080` (HTTP) и `9090` (gRPC).

## 3. Проверки безопасности: вариант 6

| Инструмент | Назначение | Команда |
|---|---|---|
| `go vet` | поиск подозрительных конструкций и вероятных ошибок | `go vet ./...` |
| `govulncheck` | проверка применимых опубликованных уязвимостей Go и зависимостей | `govulncheck ./...` |
| `gosec` | поиск распространённых небезопасных конструкций в исходном коде | `gosec ./...` |

Инструменты дополняют друг друга: `go vet` ориентирован на корректность кода, `govulncheck` — на опубликованные уязвимости, `gosec` — на security-паттерны. Ни один сканер не гарантирует абсолютную безопасность, поэтому результаты требуют анализа.

## 4. Кэширование и артефакты

`actions/setup-go@v5` включает кэширование Go-модулей на основании `go.mod`. Профиль покрытия загружается как artifact с именем `coverage` и сроком хранения 14 дней.

После скачивания артефакта покрытие можно просмотреть локально:

```bash
go tool cover -html=coverage.out
```

## 5. Проверка результата

Локальные команды:

```bash
go mod download
go test -race -coverprofile=coverage.out ./...
go vet ./...
go build ./...
```

После push нужно открыть вкладку **Actions**, дождаться завершения workflow и проверить Build, Test, `go vet`, `govulncheck`, `gosec` и Docker. Для подтверждения публикации необходимо проверить наличие тегов образа в Docker Hub.

**Статус проверки:** файлы workflow и приложения находятся в репозитории. Успешное прохождение новых запусков и публикацию образа нельзя считать подтверждёнными до завершения соответствующих workflow. Если Docker workflow сообщил, что публикация пропущена, нужно проверить, что секреты созданы именно в этом репозитории, называются точно `DOCKERHUB_USERNAME` и `DOCKERHUB_TOKEN`, и что token не был отозван.

## 6. Защита ветки

Рекомендуемая настройка GitHub: **Settings → Branches / Rulesets** — запретить прямые изменения в `main`, потребовать pull request и успешные обязательные проверки CI. Required checks следует выбирать по именам job после успешного запуска workflow.

## 7. Вывод

Настроен CI-процесс для Go 1.27.1 и актуальной стабильной версии, сборка, тесты с race detector и coverage, статический анализ, сканирование уязвимостей и отдельный Docker workflow. Публикация образа отделена от сборки и выполняется только при наличии секретов Docker Hub. Реальные результаты запусков проверяются во вкладке Actions, а не предполагаются на основании наличия YAML-файлов.
